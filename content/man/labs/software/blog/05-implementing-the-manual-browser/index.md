## Why this entry exists

The content architecture entry explained the model: directories are Hugo
sections, documents are leaf bundles, and the manual exposes only the current
directory. What it did not explain clearly enough was how that model was wired
into the project.

This entry records the implementation itself: which source files were added or
changed, what each one receives from Hugo, and how a request becomes either a
directory listing or a document page.

The change involved four layers:

```text
content/**/_index.md       page hierarchy and directory metadata
        | Hugo page graph
        v
layouts/man/*.html         branch and leaf rendering
        | shared partials
        v
layouts/_partials/man/     entries and breadcrumbs
        | CSS classes
        v
assets/sass/_custom.scss   directory-browser presentation
```

`public/` was not an implementation layer. It was regenerated by Hugo after
the source changes and remains build output.

## 1. Turning directories into Hugo sections

The first change was in `content/man/`. Directories that needed to behave as
navigable branches received an `_index.md`, including:

```text
content/man/_index.md
content/man/labs/_index.md
content/man/labs/software/_index.md
content/man/labs/software/blog/_index.md
content/man/network/_index.md
content/man/os/_index.md
content/man/thoughts/_index.md
```

There are more branch files below these paths, but the contract is always the
same. Their front matter supplies the information used by the browser:

```yaml
---
title: "software"
linkTitle: "software"
description: "Progetti e laboratori software"
weight: 30
---
```

This was not only a metadata cleanup. `_index.md` makes the containing
directory a branch bundle. Hugo then creates a section page for it and records
its parent, children, and ancestors in the page graph.

Regular documents keep `index.md` instead. For example:

```text
content/man/network/05-ipv4/
├── index.md
└── images...
```

That directory is a leaf bundle: Hugo renders one readable document and treats
the adjacent images as its resources. The difference between `_index.md` and
`index.md` is what lets the templates distinguish a directory from a file.

## 2. `layouts/man/list.html`: the directory view

This file controls the appearance and behavior of manual directories:

```text
layouts/man/list.html
```

Hugo selects it for a section created by `_index.md`. Its job is to answer “what
is immediately inside this directory?”. It does not render a long-form document
and it does not add a table of contents.

The project template replaced the theme's generic list view with this manual
specific structure:

```go-html-template
{{ define "main" }}
{{ $entries := .Pages }}
{{ if .Parent.IsHome }}
    {{ $entries = .Sections }}
{{ end }}
<div class="wrapper man-page man-directory-page">
    <main class="page-content" aria-label="Content">
        {{ partial "man/breadcrumb.html" . }}
        <header class="header man-header">...</header>
        {{ with .Content }}<div class="man-intro">{{ . }}</div>{{ end }}
        <nav class="man-browser" aria-label="Contenuto di {{ .Title }}">
            ...
            {{ partial "man/entries.html" (dict "pages" $entries) }}
        </nav>
    </main>
</div>
{{ end }}
```

Each part has one responsibility:

- `define "main"` fills the main block provided by the theme's base template;
- `.Pages` or `.Sections` selects the directory entries;
- `man-directory-page` identifies this as the directory layout, distinct from
  a readable document;
- `man/breadcrumb.html` renders the current path;
- `man-header` prints the directory title with `/` and its description;
- `.Content` prints the optional introduction written in `_index.md`;
- `man-browser` provides the `name` and `description` columns;
- `man/entries.html` renders the repeated rows;
- the `else` branch prints an explicit empty-directory message.

The collection selection at the beginning is the part that creates the
filesystem-like navigation:

```go-html-template
{{ $entries := .Pages }}
{{ if .Parent.IsHome }}
    {{ $entries = .Sections }}
{{ end }}
```

The important point is that this is not a recursive query.

- On `/man/`, `.Parent.IsHome` is true because the parent is the site home.
  The template uses `.Sections`, so the root shows only its immediate
  directories.
- On `/man/labs/software/blog/`, the condition is false. `.Pages` returns the
  immediate children of `blog`: the numbered engineering-log pages.
- Collections such as `.RegularPagesRecursive` are deliberately not used,
  because they would pull documents out of every descendant directory.

`list.html` does not know the names of any specific directory or article. It
passes the selected collection to a partial:

```go-html-template
{{ partial "man/entries.html" (dict "pages" $entries) }}
```

That separation matters: `list.html` owns the appearance of a directory page,
while the partial owns the repeated row markup.

## 3. Rendering one row per immediate child

The row implementation lives in:

```text
layouts/_partials/man/entries.html
```

Its complete loop is:

```go-html-template
{{- $pages := .pages -}}
{{- range $pages.ByWeight -}}
<li class="man-entry{{ if .IsSection }} man-directory{{ else }} man-document{{ end }}">
    <div class="man-entry-line">
        <a href="{{ .RelPermalink }}">{{ .LinkTitle }}{{ if .IsSection }}/{{ end }}</a>
        {{ with .Description }}<span class="man-entry-description">{{ . }}</span>{{ end }}
    </div>
</li>
{{- end -}}
```

This is where four visible behaviors come from:

1. `.ByWeight` follows the explicit order stored in front matter.
2. `.RelPermalink` links to Hugo's canonical page rather than constructing a
   path by string concatenation.
3. `.LinkTitle` provides the navigation label.
4. `.IsSection` adds `/` only to directories and adds a class that identifies
   the row type.

The earlier version described this as though the entry partial were doing more
than it is. It does not walk the tree and it does not decide which children are
visible. `list.html` has already made that decision; the partial only formats
the collection it receives.

## 4. Deriving breadcrumbs from ancestry

The path above every manual page comes from:

```text
layouts/_partials/man/breadcrumb.html
```

The partial starts with `~ /`, iterates over `.Ancestors.Reverse`, keeps section
ancestors, and finally prints the current page:

```go-html-template
{{ range .Ancestors.Reverse }}
    {{ if and .IsSection (ne .Kind "home") }}
        <a href="{{ .RelPermalink }}">{{ .LinkTitle }}</a><span>/</span>
    {{ end }}
{{ end }}
```

For this document, Hugo already knows the chain:

```text
home -> man -> labs -> software -> blog -> current page
```

Reversing the ancestor collection puts it in reading order. No breadcrumb
array, path map, or per-page configuration was added. If a whole section moves,
Hugo computes its new ancestry at build time.

## 5. `layouts/man/single.html`: the document view

The two manual templates deliberately serve different Hugo page kinds:

| Template | Hugo input | Responsibility |
| --- | --- | --- |
| `layouts/man/list.html` | section with `_index.md` | show a directory and its immediate children |
| `layouts/man/single.html` | regular page with `index.md` | show one readable document and its outline |

`single.html` therefore controls the appearance of documents. It does not query
children and does not render the directory browser. The current structure is:

```go-html-template
{{ $tocEnabled := .Site.Params.toc }}
{{ if isset .Params "toc" }}
    {{ $tocEnabled = .Params.toc }}
{{ end }}

<div class="wrapper post man-page man-document-page">
    <main class="page-content" aria-label="Content">
        <article class="man-document-layout{{ if $tocEnabled }} man-document-layout-with-toc{{ end }}">
            <div class="man-document-intro">
                {{ partial "man/breadcrumb.html" . }}
                <header class="header man-header">...</header>
            </div>
            {{ if $tocEnabled }}
            <aside class="man-toc" aria-label="{{ T "single.table_of_contents" }}">
                {{ partial "toc.html" . }}
            </aside>
            {{ end }}
            <div class="page-content man-document-content">
                {{ .Content }}
            </div>
        </article>
    </main>
</div>
```

The changes have specific purposes:

- `$tocEnabled` reads the global TOC setting and then allows page front matter
  to override it. This prevents an empty sidebar when `toc: false` is set;
- `man-document-page` widens only document pages enough to accommodate a second
  column;
- `man-document-layout-with-toc` activates the content-and-sidebar grid;
- `man-document-intro` keeps breadcrumb, title, and description in the main
  reading column;
- the semantic `<aside>` contains the outline generated from Markdown headings;
- `man-document-content` renders `.Content` in the main column.

The `toc.html` partial still comes from the theme. Reusing it preserves the
existing `toc` and `tocOpen` behavior. Only its position and manual-specific
presentation changed; the theme submodule was not edited. The sidebar change is
documented separately in
[06 — Moving the table of contents to the right]({{< relref "/man/labs/software/blog/06-right-hand-table-of-contents" >}}).

These files live in the project `layouts/` directory. Hugo gives project
templates precedence over matching theme templates, so the theme submodule did
not need to be edited. A later theme update therefore cannot overwrite this
implementation.

## 6. Styling the browser without changing its data model

The related styles were added to:

```text
assets/sass/_custom.scss
```

The `.man-*` rules provide:

- monospace path and directory-browser text;
- a two-column `name` and `description` grid;
- a hover state for rows;
- light and dark color variants;
- a one-column directory layout on mobile with the header row hidden;
- a wider document grid with a fixed, scroll-following TOC on the right;
- a compact, in-flow TOC below 1153 pixels.

CSS does not determine whether an entry is a page or a section. That decision
has already been made from Hugo's page object. The stylesheet only presents the
classes emitted by the templates.

## What happens during one request

For `/man/labs/software/blog/`, the complete path is now:

1. Hugo reads `content/man/labs/software/blog/_index.md` as a section page.
2. Because it is a section, Hugo selects `layouts/man/list.html`.
3. The template selects `blog`'s immediate `.Pages`.
4. `man/entries.html` sorts those pages by weight and renders their links.
5. `man/breadcrumb.html` derives `man / labs / software / blog/` from the
   section ancestry.
6. `_custom.scss` presents the emitted markup as a responsive directory list.

For one numbered article, step 2 selects `layouts/man/single.html` instead. The
article receives a breadcrumb, reading column, and right-hand table of contents,
but no child listing.
